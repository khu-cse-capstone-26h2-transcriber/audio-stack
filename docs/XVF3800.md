# ReSpeaker XVF3800 on RUBIK Pi 3

The USB array can do beamforming on the XMOS chip. The daemon opens all
channels of the chosen USB profile and selects one configured output for STT.
The ASTK engine still receives 16 kHz mono S16_LE, normally 320 samples per
20 ms frame. The daemon does not run a host beamformer or send raw microphone
channels to the engine. Use a separate multichannel recording to compare them.

## Build

On Ubuntu for Qualcomm:

```bash
bash scripts/setup_rubikpi.sh --with-rnnoise
bash scripts/build.sh Release -DASTK_ENABLE_RNNOISE=ON
ctest --test-dir build --output-on-failure
```

On Fedora, substitute `bash scripts/setup_fedora.sh --with-rnnoise` in the
first line. The Ubuntu script builds the checksum-pinned
[Xiph RNNoise 0.2 release](https://github.com/xiph/rnnoise/releases/tag/v0.2)
locally and installs SpeexDSP from the distribution. Neither step flashes or
configures the microphone. Build and run with RNNoise off if the dependencies
are unavailable; requesting it at runtime in that build is an explicit error.

## Choose the profile after plugging in

Use a data cable from a RUBIK Pi USB host port to the **XMOS USB-C port** on
the array. Some variants have a second connector for the XIAO. Verify the
device, capture PCM, formats and rates:

```bash
lsusb -d 2886:001a
arecord -l
# Replace N with the card number from arecord -l.
cat /proc/asound/cardN/stream0
```

| Reported capture format | Configuration | Use |
|---|---|---|
| 16 kHz, 2 channels | `config/xvf3800-16k2ch.conf` | Start here if the delivered firmware reports this mode. |
| 16 kHz, 6 channels | `config/xvf3800-16k6ch.conf` | One beam for STT; the same capture stream also exposes four raw microphones. |
| 48 kHz, 2 channels | `config/xvf3800-48k2ch.conf` | RNNoise comparison without first upsampling the selected beam. |

The profiles look for a single capture PCM with USB ID `2886:001a` and
open it directly via ALSA. If multiple matching PCMs exist, or the card has
a different USB ID, use `--device hw:CARD=<actual-card-id>,DEV=<actual-pcm>`.
The profile rate and channel count must match the device. There is no rate
fallback in these profiles. Avoid `plughw:` when validating a firmware
profile, since ALSA conversions can hide a mismatch.

Keep the delivered firmware if its mode is sufficient. Only change it when
you need another profile. The official
[USB firmware directory](https://github.com/respeaker/reSpeaker_XVF3800_USB_4MIC_ARRAY/tree/master/xmos_firmwares/usb)
contains distinct `_16k6ch` and `_48k2ch` images. Follow the
[Seeed USB DFU instructions](https://wiki.seeedstudio.com/respeaker_xvf3800_introduction/)
for the exact product and re-check ALSA afterwards.

## Verify the selected beam

The profiles select **USB capture channel 1**, written as `channel_index = 0`
in our zero-based configuration. Read the existing routing and confirm it
with a short recording before assuming this channel is the desired beam.
Use the vendor's [Python USB control tool](https://github.com/respeaker/reSpeaker_XVF3800_USB_4MIC_ARRAY/tree/master/python_control)
with PyUSB and libusb. For supported firmware the following checks the mode
and routes the automatically selected processed beam to the left channel:

```bash
python3 /path/to/python_control/xvf_host.py VERSION
python3 /path/to/python_control/xvf_host.py AUDIO_MGR_OP_L
python3 /path/to/python_control/xvf_host.py AUDIO_MGR_OP_L --values 6 3
python3 /path/to/python_control/xvf_host.py AUDIO_MGR_OP_L
```

The write changes the array's current routing; run it only if you want this
route. The daemon never writes device parameters. In the 16k6ch profile,
USB channels 3 through 6 normally expose raw microphones 0 through 3.
On firmware with configurable channels, read `AUDIO_MGR_OP_CH3` through
`AUDIO_MGR_OP_CH6` to verify each route. USB channel 2 is a separate
configurable output, so do not average both processed channels. USB
control permissions are separate from ALSA capture permissions.

To save an unprocessed six-channel recording of the device outputs, use
the actual PCM and format from the probe:

```bash
arecord -D hw:CARD=YOUR_CARD_ID,DEV=0 -f S16_LE -c 6 -r 16000 -d 10 /tmp/xvf-6ch.wav
```

`S16_LE` is an example; change it if the device reports a different format.
This file contains both processed and raw routes as emitted by the device;
it bypasses our host filters. Listen to each channel separately. If raw
channels are silent, check the capture switches and levels on the correct
card using the [Seeed FAQ](https://wiki.seeedstudio.com/respeaker_xvf3800_faq/).
Close the recording tool before starting the daemon on the same PCM.

## Run and compare

Set `PROFILE` to the file that matches the hardware. Start with the
device-processed beam alone and run the engine against the same socket:

```bash
PROFILE=config/xvf3800-16k6ch.conf
./build/audiostackd --config "$PROFILE" --no-backend \
  --engine-socket /tmp/astk-xvf/engine.sock

# In separate terminals:
python3 tests/dummy_engine.py --socket /tmp/astk-xvf/engine.sock
./build/astk-ctl --socket /tmp/astk-xvf/ctrl.sock status
```

Stop that run before adding RNNoise to the same profile:

```bash
./build/audiostackd --config "$PROFILE" --denoise rnnoise --no-backend \
  --engine-socket /tmp/astk-xvf/engine.sock
```

Keep `denoise = rnnoise` in a local config if it helps in the intended
environment. The supplied XVF3800 profiles leave it off so the onboard DSP
can be evaluated first; applying both may also reduce quiet speech.
The chain selects one channel, applies the optional high-pass filter,
resamples to 48 kHz when needed, runs RNNoise in 480-sample blocks and
resamples to the engine rate. SpeexDSP preserves resampler state across
short reads. RNNoise discards one initial 10 ms priming output. After an
ALSA discontinuity the host resets filter, resampler and RNNoise state.

For a short processed WAV using the same host code, set the values to
match your profile:

```bash
./build/astk-capture-wav --device auto:xvf3800 --native-rate 16000 \
  --channels 6 --channel-index 0 --no-highpass --denoise off --seconds 10 \
  --out /tmp/xvf-beam.wav
./build/astk-capture-wav --device auto:xvf3800 --native-rate 16000 \
  --channels 6 --channel-index 0 --no-highpass --denoise rnnoise --seconds 10 \
  --out /tmp/xvf-beam-rnnoise.wav
```

Before delivery, CTest exercises the shared C++ preprocessing with synthetic
stereo and six-channel data. A WAV through `snd-aloop` can exercise the
daemon as well: add `--denoise rnnoise` to the daemon options passed to
`scripts/feed_wav_loopback.sh`. The Python WAV feeder alone does not execute
the C++ filters. Verify actual USB capture, channel routing and acoustics on
the board once the microphone arrives.

For an already installed systemd service, install the rebuilt binary with
`sudo cmake --install build` after the foreground test. The unit reads
`/etc/audiostack/audiostack.conf`; update its capture and preprocessing
settings while keeping your existing engine and backend settings.
